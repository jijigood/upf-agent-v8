# UPF-Agent 向 v8 证据契约智能编排架构升级规划

> 项目：`jijigood/upf-agent`  
> 目标：在当前 Dify 外迁后的本地 UPF 运维 Agent 基础上，逐步升级为“Evidence Contract → QueryPlan → 多源证据 → K/R/P → Typed Re-evidence → Dependency-local Recompute → Action Gate”的受控智能编排原型。  
> 原则：最大化复用当前 P3/P4/P5/P6 已实现能力，不推倒重来；新增模块与专利 v8、实验验证和论文表达保持一一对应。

---

## 1. 当前系统真实基线

当前 `upf-agent` 已经不是简单的 Dify 固定工作流迁移版本，而是一个具备有限自治能力的、本地部署的、只读 Tool-using Agent。

当前可确认的主要能力包括：

- 基于 LangGraph 的有限轮次 Agent 调查流程；
- 本地模型调用、工具调用、checkpoint、resume、interrupt；
- 任务预算、工具调用预算、模型调用预算；
- `Exact + BM25 + Dense Retrieval + RRF + Qwen3 Reranker` 的 Hybrid RAG；
- 手册知识的来源 SHA、chunk、locator、版本范围校验；
- 日志结构化解析、Parquet 存储、DuckDB 查询；
- PFCP / GTP-U 等事件分类及 raised / cleared / observed 状态区分；
- 日志事件与时间、实体、拓扑的保守关联；
- TopologyEdge 的 `valid_from / valid_to` 时态字段；
- VerifiedEvidence、ToolPacket、Receipt、Journal 等证据和审计对象；
- P6 开发集 / heldout / 人工复核 / freeze / 单次留出集等实验治理体系。

当前仍未完整实现的 v8 核心能力：

- 显式 Evidence Contract；
- Contract → QueryPlan Compiler；
- K / R / P 状态机；
- 双侧边界证据匹配；
- 状态驱动的 Typed Re-evidence；
- 字段级 DependencyIndex；
- Dependency-local Recompute；
- 三类逻辑证据图与 GraphRAG；
- ActionCandidate 与 ActionGate；
- 受控写操作、回采和回滚。

因此当前升级重点不是重写基础工程，而是补齐“结构化证据需求与受控编排层”。

# 2. 总体升级架构

```text
Current stable system
────────────────────────────────

Task
 ↓
AgentTask
 ↓
LangGraph
 ├── Hybrid RAG
 ├── Log tools
 ├── Topology tools
 └── VerifiedEvidence

                    ↓ evolve

V8 orchestration layer
────────────────────────────────

Task
 ↓
AgentTask
 ↓
EvidenceContract
 ↓
QueryPlanCompiler
 ↓
 ┌──────────────┬───────────────┬────────────────┐
 │              │               │                │
Hybrid RAG   GraphRAG       Runtime Tools     Topology Tools
 existing      NEW             existing          existing
 │              │               │                │
 └──────────────┴───────┬───────┴────────────────┘
                        ↓
                 EvidenceBinding
                        ↓
                   K / R / P
                        ↓
                    GapRouter
                        ↓
              Targeted Re-evidence
                        ↓
                 DependencyIndex
                        ↓
                 LocalRecompute
                        ↓
          Diagnostic Candidate + ActionCandidate
                        ↓
                    ActionGate
                        ↓
          Suggest / Re-evidence / Human
```

核心设计原则：

1. LLM 负责理解、规划、解释和候选生成；
2. K/R/P、版本、时效、权限、边界一致性、依赖更新和 ActionGate 由确定性代码实现；
3. 现有 Hybrid RAG、日志解析、拓扑工具、LangGraph 和 P6 评估体系全部保留；
4. GraphRAG 作为新增证据图通道，而不是替换当前 Qdrant / BM25 / Reranker；
5. 第一阶段只做只读建议，不做真实网络配置下发。

# 4. V1：Evidence Contract + QueryPlan

## 4.1 保留 AgentTask

当前 `AgentTask` 继续表示：

- 用户问题；
- product / version；
- device_ids；
- time_window；
- log_generation；
- topology_generation；
- manual_generation；
- budget。

它解决的是“允许访问什么任务范围”。

Evidence Contract 则解决“完成判断必须有哪些证据”。

---

## 4.2 新增 Evidence Contract

建议 `orchestration/contract.py`：

```python
class EvidenceClass(StrEnum):
    KNOWLEDGE = "K"
    RUNTIME = "R"
    BOUNDARY = "P"


class RequirementStatus(StrEnum):
    UNKNOWN = "unknown"
    SATISFIED = "satisfied"
    MISSING = "missing"
    NOT_APPLICABLE = "not_applicable"
    STALE = "stale"
    CONFLICT = "conflict"


class ObjectRef(StrictModel):
    domain: str
    object_type: str
    object_id: str


class EvidenceRequirement(StrictModel):
    requirement_id: str
    evidence_class: EvidenceClass
    object_ref: ObjectRef
    required_fields: list[str]

    product: str | None = None
    version: str | None = None

    interface_type: str | None = None

    time_window: TimeWindow | None = None
    freshness_seconds: int | None = None

    path_position: str | None = None

    permission: Literal["read", "suggest", "execute"] = "read"

    mandatory: bool = True


class EvidenceContract(StrictModel):
    contract_id: str
    run_id: str
    template_id: str
    requirements: list[EvidenceRequirement]
    compiler_version: str
    contract_hash: str
```

要求：

- Contract 必须是 machine-checkable；
- 不把自由文本 Prompt 当作 Contract；
- requirement 必须明确对象、字段、时间、版本、权限和证据类别。

# 12. K：Knowledge Applicability

K 主要判断：

- source 是否存在；
- object 是否匹配；
- product 是否匹配；
- version 是否适用；
- required_fields 是否齐全；
- source 是否可追溯；
- 证据是否满足 Contract 当前用途。

示例：

```text
Requirement:
UPF 5.0
requires:
  troubleshooting_procedure
  version

Retrieved manual:
version = 4.x
```

结果：

```text
K = NOT_APPLICABLE
reason = VERSION_MISMATCH
```

不能因为“检索到了相关文本”就视为满足。

---

# 13. R：Runtime Evidence

R 主要判断：

- required_fields 是否完整；
- timestamp 是否可用；
- timezone 是否明确；
- evidence 是否落在 observation window；
- freshness 是否满足；
- device identity 是否明确；
- tool receipt 是否成功；
- 多来源当前值是否冲突。

示例：

```text
timestamp_utc = null
device_id = null
```

结果：

```text
R = MISSING

missing_fields:
  - timestamp
  - device_id

reasons:
  - TIME_UNKNOWN
  - IDENTITY_MISSING
```

# 18. Local Recompute

`orchestration/recompute.py`：

```text
changed evidence
       ↓
diff fields
       ↓
mark reachable readers INVALID
       ↓
queue = direct readers
       ↓
recompute node
       ↓
compare:
  state code
  validity
  judgement basis
       ↓
if changed:
  enqueue successors
else:
  preserve unaffected readers
       ↓
queue empty
```

关键要求：

不能只比较：

```text
old_state.status == new_state.status
```

还必须比较：

- judgement_basis；
- actual evidence values；
- version；
- provenance；
- validity window。

例如：

```text
CPU 30% → 90%
R status 仍为 SATISFIED
```

如果动作要求 `CPU < 80%`，ActionGate 仍必须重算。

# 19. Full vs Local Baseline

```text

evidence
facts

```

> Full / Coarse Invalidation baseline。

实验：

```text
B0 Current Full/Coarse Recompute

vs

B1 Dependency-local Recompute
```

核心指标：

- State Consistency；
- Action Decision Consistency；
- Recomputed State Count；
- Tool Calls；
- Retrieval Count；
- LLM Requests；
- Latency；
- Dependency Recall。

正确性要求：

```text
Final State(Local) == Final State(Full)

Action Decision(Local) == Action Decision(Full)
```

效率提升是第二目标。

# 28. ActionGate


> 不 fork 一个大型 GraphRAG/Agent 项目重做 `upf-agent`，而是保留当前仓库作为主工程，从不同开源项目中复用成熟的基础能力；专利 v8 的 Evidence Contract、K/R/P、Typed Re-evidence、Dependency-local Recompute、ActionGate 仍由本项目自己实现。

3. **后期实验平台**：仅用于真实 5GC 运行证据和故障场景生成。

## B0：当前 Hybrid RAG

直接使用当前：

```text
p3_search.py

Exact
+
BM25
+
Qdrant Dense
+
RRF
+
Qwen Reranker
```

这是现有稳定 baseline。

---

## B1：Ordinary GraphRAG

可以直接使用：

```text
neo4j-graphrag-python
HybridCypherRetriever
```

逻辑：

```text
query
↓
vector/fulltext seed
↓
fixed Cypher traversal
↓
graph context
```

它适合作为普通 GraphRAG 对照组。

---

## Ours：Contract-constrained Graph Retrieval

本方案不建议直接把 `HybridCypherRetriever` 当成最终实现。

推荐：

```text
Current p3_search
      ↓
top-k source chunks / entities
      ↓
Graph seed mapping
      ↓
EvidenceRequirement
      ↓
GraphQueryPlan
      ↓
ContractCypherCompiler
      ↓
bounded Cypher traversal
      ↓
EvidenceSubgraph
```

也就是说：

> 当前成熟 Hybrid RAG 继续负责找到语义种子，Neo4j 负责关系扩展，Evidence Contract 决定允许扩展什么关系、对象、时间、版本和范围。

这样最大程度复用现有 P3。

# 55. 推荐新增 ContractCypherCompiler


接口：

```python
def compile_graph_query(
    requirement: EvidenceRequirement,
    seeds: list[GraphSeed],
    policy: GraphQueryPolicy,

    ...
```

输入：

```text
target object
allowed relations
path position
time window
version
max hops
max nodes
source requirements
```

输出：

```text
Cypher
parameters
required return fields
provenance fields
```

例如：

```text

  object = UPF-A
  interface = N4
  evidence_class = P

Allowed relations:
  HAS_INTERFACE
  CONNECTS_TO
  PEER_OF

max_hops = 2
```

只允许查询相关 N4 子图。

这部分是本项目应该自己实现的核心，不建议直接交给通用 GraphRAG 框架。

# 61. NetworkX：DependencyIndex 的最快实现

推荐：

```text
networkx/networkx
```

这一部分建议直接作为依赖。

第一版甚至不用 Neo4j 来存 DependencyIndex。

原因：

> Evidence Graph 是“网络世界里的关系”，Dependency Graph 是“程序计算读取关系”，二者不是同一张图。

使用 NetworkX 建立：

```text
EvidenceField
↓
RequirementState
↓
RequirementState
↓
ActionGate
```

例如：

```python
import networkx as nx

g = nx.DiGraph()

g.add_edge(
    "field:E1:peer_ip",
    "state:R_PFCP",
)

g.add_edge(
    "state:R_PFCP",
    "action:CHECK_N4",
)
```

变化后：

```python
affected = nx.descendants(
    g,
    "field:E1:peer_ip",
)
```

但真正重算顺序、状态比较、judgement basis 比较仍然由自己的 `recompute.py` 实现。

这些才是专利核心逻辑。
