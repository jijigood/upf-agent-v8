## 2. 怎么填写与核对版本

统一新包 `public/input-index.json` 有中性ID、材料路径、输入指纹。复制 `public/reviewer-1.csv` 到新的个人工作目录填写；第二位独立人员使用 `reviewer-2.csv`，不要覆盖冻结模板。在 `reviewer` 填真实姓名或代号；`decision` 填 `approve / conditional / revise / reject`，分别为批准、条件接受、需修订、拒绝。`source_locators` 写具体文件、字段或日志行，`rationale` 写可追溯原因，不只写“通过”。

两位评审分歧另建仲裁记录，保留双方原意见与第三次决定；没有第二位人员时明确记录单人审核，不代填另一席位。`organizer-only/source-map.json` 用于组织者回映原批次；给独立评审只提供 `public/`，不能先给答案或方法标签。风格可能透露方法，所以仅登记匿名材料，不宣称已完成严格盲评。

该包 `sha256_manifest.json` 覆盖完整冻结文件；`input_sha256` 是入口文件组合的digest，数据文件还需关联完整manifest，不能只签一个raw-plan hash而省略来源版本。新复核记录注明批次、匿名ID、入口digest、材料manifest hash、评审者、时间与判定。E2/E3/E5/E7可使用同样字段另存CSV，不修改原始运行JSON或 `reviewed=false` 文件。

## 3. S2：复核什么、如何判断

先审参考再审原文；不要由模型输出反推参考。每个参考打开 `case-task.json`、`case-spec.json`、`case-reference.json` 及 `data/`。逐项检查：

- [ ] 题目目标与结构化需求一致；N3是UPF/RAN，N4是UPF/SMF；各产品版本与物理材料一致。合成RAN/SMF操作只能标为开发材料，不能解释成真实厂商流程。
- [ ] 13–16只要求手册流程，不要求无关映射。参考所需步骤有真正可见依据，不缺必要调查，不因转人工删掉合法步骤。
- [ ] 完整映射的双方P与服务／mapping／端点／方向匹配，两端身份是DAG先行步骤。缺侧、冲突、陈旧材料只能产生明确条件调查或停止／补证，不能当当前已核验。
- [ ] 参考允许分支确实覆盖合理多解，不因某一个模型措辞而定唯一答案。确认所批准版本与digest。

每份原文打开 `raw-plan.txt`、`task.json`、`bindings.json`，对照真实 `data/`。先从原文定位映射步骤 evidence，再逐条找到物理P对象、时刻和字段；不能只看自动 `validation.json`。沿 `depends_on` 检查两端身份是否都是先行依赖。`basis=collect_then_verify` 的 pending 要对应实际缺口，必须写清未补齐停止，不能声称已完成。调查文本的进程状态、接口端点、版本和手册步骤也要与源一致。

pilot-07／pilot-16的P5原文未得到K且缺配置步骤：先核对其实际bindings、P5工具trace与参考要求，再判断遗漏。不能给原文事后补引、不能把工具未拿到的知识解释成已知。

## 4. E2/E3/E5/E6：如何沿来源审查

**E2：** 对每查询比较题目、task/contract需求、query-plan字段、实际来源对象与时间。R文本需真正要求runtime接口字段，P文本需双方映射；K对每片段核对locator、章节和hash。明确“相关片段”与“合并后完整操作”两种标签；当前后者未批准，应保持空白，不能仅凭检索命中填质量通过。预设错版／无适用证据控制也按用途判定，保留控制性质。

**E3：** 从 `references.json` 取预声明primary，再对 `inputs/case-NN` 的发布目录逐轮检查当时可见内容。用结果中的primary_closed与all_closed分别判断；25/26的工具预算耗尽和29–32的空观察不是待补造的数据。查看每方法rounds、dispatch、Ledger提交回执，失败／未提交不能计为有效证据或正确停止。模型未来发布内容不可提前可见。

**E5：** 先看匿名候选与真实输入，不先看开发allowed/forbidden标签。002公开文件名为 `candidate-review-view.txt`／`visible-input-review-view.json`，仅batch标识匿名化；精确原文在organizer-only。先按review view审语义，再由组织者核对原文hash与映射，不能把view当原始模型输出。旧001包因batch标签泄漏保留为历史。尤其核对P双方、身份DAG、只读权限、K对象适用性，以及binding的observed/valid与物理源是否一致；物理源新鲜不能覆盖旧binding。新来源机械报告是线索，不是语言语义判断。对旧forbidden-09-01/02原辅助意见另记纠正，不修改旧意见文件。

**E6：** 每对打开base-task、changed-task、两份data及mechanical-proof；逐项对比目标、接口、对象角色、产品版本、权限、时刻、双侧字段和冲突是否保留。改字段顺序、无关字段、同义文字与证据别名应保持语义；机械proof只能证明定义内字段，不替代自然语言核查。原80份意见只对应旧hash；新版本可复用审查思路但需新记录。

## 5. E7：先看正常材料，再核对真值

为避免由注入标签推断答案，第一遍不要打开 `private/`。每轮按以下顺序：

1. 打开 `input/snapshot.json`：实际进程状态、配置、当前窗口日志、normal探针与抓包；区分S=正常睡眠和T=停止调度。下行探针目标必须对应实际UE TUN地址；未取得地址要标未尝试，不能当有效丢包观察。
2. 打开 `agent/facts.json`：每个f编号有原始locator、来源SHA、日志行／包字节定位。再看 `model-visible-facts.json`：正常字段投影、log省略数、抓包分组。模型没有看见省略事件，不能以此断言没有某记录。当前原型7保留原型5实现，按E/S/PN可选字段和扩展头链提取内层IP/ICMP，并保存TEID、头长及解码错误。null仍可能表示截断、非IPv4或未覆盖协议，不能判成不存在该事件。原始捕获文件保留，但snaplen=256不保证全部线上负载。PFCP完整IE和双侧会话映射未实现。
3. 打开 `raw-model-output.json` 与 `root-cause-report.json`：逐候选检查rationale/evidence_ids，逐调查步骤检查target/action/text/refs。`S`被解释为服务暂停、看到INPUT之前的包被解释为应用收到、把SMF当N3端点、看到请求就声称双向会话成功等，均需逐项指出。
4. 确认 `execute_authorized=false`、`goal_achieved=false`、步骤claimed_executed=false。真实引用不等于推理正确；只读步骤也要有意义、可执行且不越过对象范围。
5. 首轮意见落盘后，组织者查看 `private/round-NNN/truth.json`、`external-verification.json`、`health-after.json`，核对故障族Top1/Top3及独立恢复。NF重置是harness复位，不记成模型修复或MTTR。

辅助填写入口已在 `review-remediation-20261010/supplement-review-index-001/` 提供：E2 96、E3 32、E6输出540、E7 60，共728条，两个真实评审席位都保持空白。`source-sha256.json` 固定实际文件，`input-index.json` 给出具体路径；E7表不含注入标签，第一遍仍只看正常输入。此索引不提供匿名承诺，E6全540条保留不等于要求无差别重审全部已有材料；优先复核9份未匹配与其他实际分歧，再按批准协议确定抽样范围。S2两例＋E6九例的逐原文路径、SHA和实际K绑定数量在 `review-remediation-20261010/draft-reference-disagreements-001.json`；目前E6九例均为pilot-07/P5，它仅登记参考分歧，不生成语义批准。

优先审查 `review-remediation-20261010/e7-semantic-review-concerns-001.json` 的两个实际例句：它说明Top1代码正确时调查理由仍可能缺依据。该文件是待评线索，不是专家签署，不将其自动导入正式失败或批准标签。
