# 安装、复现与恢复

在当前机器与已有共享权重/服务条件下复现。应用 Python 3.11，主应用 `.venv-v8` 和对照 `.venv-graphrag` 分开。锁文件冻结主应用所有解析版本，对照 requirements 包含哈希。运行数据和模型资源分开；快照不包含共享权重、私有 Neo4j 密码、完整 Docker 数据卷，也不是跨主机离线交付包。

```bash
cd /home/huangxiaolin/upf-agent-v8
UV_PROJECT_ENVIRONMENT=.venv-v8 uv sync --locked --extra dev
.venv-v8/bin/python -c 'import upf_agent; print(upf_agent.__file__)'
uv pip sync --python .venv-graphrag/bin/python requirements/v8-graphrag.lock
.venv-v8/bin/pytest -q
```

首次构建运行根用 `.venv-v8/bin/python scripts/v8_prepare.py`。该脚本固定原工作区指纹、复制原件与 P2 数据库、新建配置身份和检索索引 generation、复用经校验向量；交付运行根已准备好，无需重复执行它。修改检索配置后必须重新构建相应 generation，不能编辑旧 manifest 绕过校验。

```bash
.venv-v8/bin/python scripts/v8_neo4j.py
.venv-v8/bin/upf-agent v8 graph build
.venv-v8/bin/upf-agent v8 run --task runtime/v8/examples/upf_n4_fault-task.json
.venv-v8/bin/upf-agent v8 inspect --run-id <run-id>
.venv-v8/bin/upf-agent v8 resume --run-id <run-id>
```

Neo4j 仅使用本机 `17474/17687` 与独立卷；脚本启动前检查端口。私有 `runtime/v8/config/v8-neo4j.json` 模式为 0600。API 默认 Memory，可将新任务 `graph_backend` 改为 `neo4j`。恢复已有任务不能修改权限、对象或代码环境；如代码变化，恢复对应快照与代码版本。报告目录是 `runtime/v8/runs/v8/<run-id>/`，含 JSON、Markdown、GraphQueryPlan 和每轮 subgraph JSON。账本、checkpoint、依赖和更新回执位于 `runtime/v8/data/v8/`。

开发与主实验命令：

```bash
.venv-v8/bin/upf-agent v8 evaluate --suite dev --batch dev-new-001
.venv-v8/bin/upf-agent v8 evaluate --suite agent --batch agent-new-001
.venv-v8/bin/upf-agent v8 evaluate --suite graph
.venv-v8/bin/python scripts/v8_local_matrix.py \
  --root runtime/v8 --output runtime/v8/experiments/v8/local-new-001 --workers 4
```

`evaluate --suite local` 也支持串行完整矩阵。以上模型实验需现有 `18000` 服务，图检索需 `cuda:1` 检索模型和专用 Neo4j。正式 `heldout-final-001` 已消费后不能再次作为新留出验收；使用新的真正独立结构/来源组才能进行下一次盲验。`evaluate --suite all` 会涉及一次性留出，不能用于日常重复回归。

快照前停止本轮运行并等待实验完成。脚本取得运行根排他锁，SQLite 使用 backup API，每个文件保存 SHA；目标已存在即拒绝，私有密码与链接不打包。

```bash
.venv-v8/bin/python scripts/v8_snapshot.py snapshot runtime/v8 artifacts/v8-new-snapshot
.venv-v8/bin/python scripts/v8_snapshot.py restore artifacts/v8-new-snapshot runtime/v8-new-restore
.venv-v8/bin/upf-agent v8 resume --root runtime/v8-new-restore --run-id <暂停的run-id>
```

恢复会先校验所有快照文件，再复制到新运行根并连接本项目现有 tools/retrieval 环境。备份中 `project/` 保存代码、工具脚本、配置、锁、测试、说明和样例；当前机器复现须使用这些相同代码和包版本。记录的原生 P2/P3/P4 配置含本机绝对路径，本轮同机恢复使用对应已存在共享资源；移机必须做受验证迁移并新建 generation。

已消费留出可做“已知输入回放”，不计为新盲验。下列脚本校验冻结代码/配置/来源 SHA，重跑完整 Ours 流程并与独立全量及原 oracle 比较；对照方法按已保存模型原始建议重新核算。它不再次请求模型来创造新验收成绩，延迟和模型输出只能用原实验记录。

```bash
.venv-v8/bin/python scripts/v8_replay.py --root runtime/v8-new-restore \
  --freeze runtime/v8-new-restore/experiments/v8/heldout/heldout-final-001/freeze.json \
  --output runtime/v8-new-restore/experiments/v8/known-input-replay-001
```

外部依赖及实际包版本在 `runtime/v8/evidence/u0/environment.json`；56 个权重文件的 SHA 验证记录、模型服务型号、原件指纹和隔离回执也在 `evidence/u0/`。冻结方法矩阵、任务、oracle、原始响应、CSV 和来源回指在每个实验批次。复现验证明细与实测结果见验收报告。

## 本轮实际恢复结果

验证快照为 `artifacts/v8-restore-validation-20261007/`，新根为 `runtime/v8-restore-validation-20261007/`。已核验 2,721 个恢复文件的 SHA 和六个 SQLite 的 quick_check，并恢复暂停任务 `5b6cfc59df4144818bdae5f34d20c559`。首次恢复生成三条只读工具回执和六条证据 revision，后续重复恢复的 SQL 行、预算和结果保持一致。原运行根的该任务仍暂停。

全部 11 个冻结场景在新根回放通过，完整状态/动作与独立全量及原 oracle 一致。回放模型调用为 0，对照方法使用存档原始建议重新核算。回执位于 `runtime/v8/evidence/u6/recovery-validation.json` 和 `known-input-replay-001/`。

最终快照为 `artifacts/v8-final-20261007/`，另提供同名 `.tar.gz` 与 `.sha256`。这些目录按版本封存，备份命令拒绝覆盖；如需运行，先恢复到新目录。文件数量、最终 manifest 和压缩包 SHA 见 `docs/v8/delivery-receipt.json`，该回执在封包后生成并置于快照之外，避免对自身校验和形成循环依赖。现有验证恢复根已使用，不可再次覆盖它；重做验证请使用新的目录名。

图/串行实验的默认输出目录固定，重复开发运行应使用新的恢复副本，或使用带新 output 的规模实验脚本。已有正式留出记录始终按已消费处理。
