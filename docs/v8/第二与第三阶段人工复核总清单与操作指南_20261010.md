## 3. 所有项目共同采用的核验方法

### 3.1 先确认任务边界

- [ ] 读任务 `question`、`template`、`objects`、`path.positions`，确认要调查哪几个对象、哪个接口和双侧关系。
- [ ] 读 `product`、`version`、`as_of`，按任务评价时刻核对材料。不要用复核当天时刻替代固定的实验时刻。
- [ ] 读 `permission.objects/domains/readable_fields/execute`。能在评审底稿里看见，不能说明方案有权读取。
- [ ] 明确“只读调查方案可成立”和“根因已确定／网络已恢复”是不同结论。
- [ ] 明确材料是否合成。除 E2 引用的实际手册文段外，相关任务、映射和观察大量采用开发 fixture；不能当成现网独立事故。

### 3.2 如何追到原始来源

证据 `source.relative_path` 相对于该证据的**案例／运行根目录**。定位方式为：

```text
实际文件 = 对应案例或运行根目录 / source.relative_path
原始记录 = 实际文件中 source.locator 指向的位置
```

`/observations/1` 指 `observations` 数组第二条，数组从 0 开始。`false` 是已观察布尔值，不等于缺失；`null`、无字段、冲突、陈旧、版本未知和权限拒读分别记录。

| 类型 | 要核对的原始内容 | 不可直接推出的结论 |
|---|---|---|
| K：手册／知识 | 原文、产品／版本／对象／用途、知识登记依据、有效期与撤销 | 手册规则不能自动证明现场已配置或根因已确认 |
| R：运行观察 | 对象、接口、字段和值类型、版本、观测窗口、冲突和权限 | `down`、小 MTU 或配置关闭不能直接当成唯一根因 |
| P：对端／映射 | 两端对象、local/peer endpoint、方向、服务、映射／配置版本和时刻 | 单侧资料不能代替双侧一致性核验 |

`reviewed=false`、`trusted_rule`、`synthetic=true`、`corroborated=true` 都要结合来源理解，不能单凭字段名称证明领域正确。

### 3.3 每个问题怎样写才可处理

每条意见至少包括：**案例／查询／匿名 ID → 文件 → 分支或 step_id → 来源 locator／chunk_id → 哪个事实支持意见 → 影响 → 建议处理**。

可以照下面的格式写；其中内容是填写提示，不是已作出的审批：

```text
项目 ID：填写真实 ID
检查项：例如 R09 / P06 / E6-语义
问题位置：文件路径 + any_of 分支 / step_id / JSON 字段
来源依据：物理文件 + /observations/N 或 chunk_id、原文段落
观察：逐项写清与任务、参考或原文不一致的内容
影响：错对象 / 错依据 / 漏关键步骤 / 语义变化 / 仅表达问题
处理建议：修改参考 / 补材料 / 暂无法判断 / 其他具体处理
```

只有“通过”“不合理”或“机器也是这样判的”无法支持后续修订与仲裁。

1. 在公开索引搜索对应 query，写下需求对象、字段、用途、产品版本、时刻和权限。
2. K 查询先搜索 chunks 档案中的关键词／章节。读命中文段及必要上下文，再按 `relative_path` 打开 `corpus/data/raw/<relative_path>` 中原 DOCX。`locators` 例如 `word/document.xml/body/p[3]` 是 XML 段落定位，不是 Word 页码；表格与标题上下文也要核对。

4. 独立列出相关且适用的证据／等价证据集合，说明每个成员支持哪个必需字段。K 可记 chunk_id；R/P 可记证据／节点标识，并附物理文件和 locator。
5. 判定没有适用来源时，写清排除理由；“检索没有返回”不足以证明源中不存在证据。
6. 再比开发参考与五方法返回，区分“参考需改”“检索漏召回”“返回不适用证据”“只可作线索”。

- [ ] 等价证据集合覆盖合法替代来源，不把唯一开发 target_chunk 当成唯一合法答案。
- [ ] 时间与权限满足任务限制；图关系有来源佐证，没有因为路径存在就认定证据适用。
- [ ] 无证据、种子交接失效及合法 reseed 的构造条件与原材料一致；构造标签不是人工真值。

- [ ] 对标签不一致、理由实质冲突、无法判断项逐项处理；同为 approve 不代表所有问题自动解决。
- [ ] 需要改参考／任务／扰动时另存新版本、记录差异和新 hash，重新确认；旧记录不覆盖为“双方一致”。
- [ ] 只有参考标签改变时评估另批重评分；输入、证据、代码、prompt 或生成协议改变时评估是否需要另批运行。

### 6.2 交回哪些文件

| 工作 | 交回内容 |
|---|---|
| 第二阶段参考 | 实际逐例 Markdown／JSON、参考版本及 digest、两人身份、范围解释、分歧处理 |
| 第二阶段原文 | 两份已填 CSV、详细意见附件、使用的批准参考 digest；已有审核的实际来源 |
| 第三阶段 | 八份已填 CSV、详细意见附件；证据集合、发布轮次、步骤定位或语义对比完整 |

第三阶段 CSV 的共同字段：`reviewer_name`、`review_date` 为实际身份和日期；`rationale` 写判定理由；`source_locators` 写物理证据；`needs_arbitration` 用 true／false 或未确定时空白。未完成项不要填“通过”；无法判断须说明材料缺口。

不要求你再次运行模型、手工计算 hash 或编辑数据库。组织者负责格式核验、忠实转换、导入和后续复算；技术核验不能替代评审专业性与独立性判断。

### 6.3 现有导入工具到底支持什么

第二阶段**参考双评**已有 [v8_phase2_review.py](../../scripts/v8_phase2_review.py)。真实记录整理成 JSON 数组后，在项目根目录运行；输出必须使用新目录：

```bash
.venv-v8/bin/python scripts/v8_phase2_review.py \
  --pilot runtime/v8-next/phase2/reference-revision-002 \
  --reviews /实际完成的参考双评记录.json \
  --output runtime/v8-next/phase2/实际新复核结果目录
```

以上是组织者用法示意，路径需换成实际记录。脚本核验 case_id、当前参考 digest、不同 reviewer 和 approve/request_changes；生成新审核产物，不修改旧参考或原文。不能把第三份仲裁记录直接塞进原两人数组代替新版本确认。

**该工具不接收第二阶段原文 CSV，也不接收第三阶段 E2/E3/E5/E6 CSV。** 这些人工判定目前需要组织者整理、核验并接入对应参考／评分流程；不得把“文件已填”说成“系统已导入”或自动修改 reviewed。存在待判项时继续保留正式 VPR 未完成。
