## 场景与预冻结参考

32 条新合成开发输入分为八类，每类四种发布条件：第 1 轮可修复、第 2 轮可修复、永久不能修复、表面修复但仍不合法。固定权限拒绝和完全无来源两类均不可补，不能扩大权限或凭空产生来源。因此实际分母是 **12 条可补、20 条不可补**，不是每类强凑正反各半。

| 缺口族 | 初始物理事实 | 合法修复或不可补条件 |
|---|---|---|
| knowledge-version-unknown | UPF-A 的 K 版本未声明 | 新发布明确 5.0；错版 4.0 不构成修复 |
| runtime-timezone-unknown | 只有无偏移的本地时间文本，observed=null | 新来源明确声明 UTC 观察窗；不猜时区 |
| stale | R 观察窗距固定评估时刻超过 freshness | 新版真实声明新鲜观察窗；错版的新鲜窗仍不适用 |
| one-side-missing | 缺 SMF-B 的 P 记录 | 新版声明对端记录；错版对端不能闭合 |
| boundary-conflict | 两侧 peer_endpoint 不匹配 | 双侧一致的新发布；只改 endpoint 而 config_version 冲突仍不闭合 |
| permission-denied | scope 缺 n4_enabled 读权限 | 保持拒绝，既不扩大 scope，也不泄漏该字段 |
| tool-unavailable | 证据服务 unavailable | 可补条件为后来真实恢复；永久 unavailable 保留缺口 |
| no-source-exists | 所有轮次 observations=[] | 不生成替代来源，停止并保留缺口 |

所有参考 synthetic=true／reviewed=false。每例有独立文件和 ID，但共用 `example-v8-N4-1` fixture family，八族内部相关；不当成 32 起独立事故，不计算总体置信区间。该矩阵未覆盖真实来源、任务本身版本未知或所有跨域拓扑变化，正式扩量前需独立参考审查。

## 发布、权限、时间与去重

1. 在任何方法评价前写出全部不可变来源、registry、task、Contract 和未审参考，保存逐文件 SHA。
2. 轮次决定哪些已登记来源开放；后端只把当轮完整发布版交给实际适配器。未来路径/hash 是公共 capability 目录，未来观察正文不会进入模型。
3. 新完整发布版在物理 JSON 中声明 `edition/complete/supersedes`；每个实际观察有 `slot_id`。同一逻辑槽采用同一 evidence_id 和递增 revision，显式替代旧版，不把相冲突的旧版悄悄当作仍然当前的事实。
4. 同一发布版的再次查询保留初次绑定回执，新增查询回执单独计费；重复调用不能改写已提交证据。
5. task、Contract、权限与 task.as_of 全程固定。轮次开放新来源，不等于把评估时刻往前推；未声明的时间不推断。
6. T3 调用原有 `route_gaps/compile_gap_plan`。只有发布内容/可用性改变或出现尚未查询的需求才解锁查询；无变化轮次不收费，有公开的后续发布才等待，否则停止。
7. 每批以真实 Ledger 最新 revision 求值，使用既有 LocalEvaluator/FullEvaluator/动作 Gate，并核对完整状态、认证上下文和动作结果；执行授权始终 false。

本次是显式启用的实验 harness。生产 Engine 的静态取证与停止规则未改，不能说生产默认入口已经具备动态发布服务。

## 四方法与成本解释

- T0：相同初始编译取证后不补证。
- T1：每轮完整刷新仍可读取的所有 K/R/P，计入无变化成功重复查询。
- T2：真实原生 P5 自主规划／取证／停止；使用现有图、工具 cache 和预算，不手写选择器，不帮其补缺口。后端随原生规划轮次开放来源。
- T3：按真实类型化缺口定向查询；服务恢复后漏查新 P 的粗粒度去重已修订为工具／对象／需求。

共有上限：8 工具、8 模型、3 轮、180 秒。P5 沿用已有 runner 的一模型生成头预留，实际规划最多 7 次；本实验没有共同方案生成头，该预留不计为实际模型调用，额外限制单独披露。初始 seed 与初始编译查询全部计入成本。

**接口粒度限制：T0/T1/T3 的 read_observation 可以在一次对象查询中取得多类证据，原生 P5 的公开手册、日志、拓扑工具分开。** 两边有相同物理来源、权限、发布目录与上限，但不能把跨接口的调用次数直接归因于规划效率。本批 T1/T3 使用同一接口，其工程成本可以对照；完整正式四方法公平性还需统一查询粒度或增加等价动作成本的专门控制。 P5 原生 confirmed_task 未包含 v8 的 task.as_of／完整 freshness 规格；因此本批不能作为纯调度机制优势的正式因果结论，后续须补齐公共任务规格。

指标解释：

- 主要缺口关闭与全契约关闭同时保存，不用一个成功需求掩盖残留需求。
- 假关闭：预声明不可补场景在共同规则中被判主要需求 satisfied。该工程指标不等同于自然语言报告的虚假结论，后者仍需原文审查。
- 正确停止：不可补主要需求仍开放，且在预算内正常终止；不把 runner 异常或未提交回执当正确停止。不表示“最早停止”，查询效率另报。
- 新有效字段：对象／类别／必需字段／值首次进入 satisfied 需求，含初始取证及双侧齐备后获得的可用性；不是物理 I/O 读数。
- 重复成功查询：同工具／对象／需求／参数、同发布内容，在先前成功查询后重复；负结果和服务错误不自动算冗余。
- 模型 tokens 采用真实响应 usage；缺失仍为 null。工具／模型是 dispatcher 计数，未声称已测所有文件或网络的物理读次数。

## 早期试验与失败保留

`e3-engineering-001` 保存首版 96 次工程试验：T1/T3 的主要可补需求均关闭，但 T3 的两例服务恢复任务仍缺 SMF-B 的 P；该首轮只保存源码指纹，未提供与该版完全等同的单独工作树快照，不用于正式复现结论。此后诊断发现工具/对象级“已查询”把早先的 K/R 查询误当成已查询 P。修订去重粒度后 36 项专项覆盖八族四种发布条件和该残留反例，要求可补场景全契约关闭。

## 完整矩阵结果

首轮 128 次原汇总把 4 个 reserved 回执漏掉，不能引用其 pass=true 作为最终验收。第二版只读复算 [`e3-four-methods-audit-002.json`](../../runtime/v8-next/phase3/e3-four-methods-audit-002.json) 为 pass=false，明确列出 e3-25 至 e3-28 每例 1 个未提交、实际已尝试却报 0 次的调用。

该错误包用了 ToolPacket 不允许的 tool_unavailable，原生图将 ValidationError 捕获为失败，外层异常字段未发现。修为标准 tool_failed，新增尝试/提交/未提交三个计数及验收拒绝；非 retryable 服务故障实际一次查询后停止，正确保留不能自动等待恢复的 P5 行为。第一版审计的通过只覆盖来源/已提交回执，缺少 pending 检查，作为开发记录保留。

修订后按新冻结源码完整重跑 128 次，没有拼接旧结果；两个完整批次的 **241 份评价前输入 hash 完全相同**。最终 [`summary.json`](../../runtime/v8-next/phase3/e3-four-methods-003/summary.json) 与 [`只读复算`](../../runtime/v8-next/phase3/e3-four-methods-audit-003.json) 均 pass=true，integrity_errors=[]。

四个服务不可用原生 P5 案例现均 **实际尝试 1、提交 1、未提交 0、模型 0**，使用合法 tool_failed 回执；没有 ValidationError。固定权限未扩大，n4_enabled 不泄漏，执行授权始终 false。全部 128 次满足 8/8/3/180 上限，最长实测 36.18 秒。
