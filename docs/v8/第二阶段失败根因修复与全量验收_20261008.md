# 第二阶段失败根因修复与全量验收

启动日期：2026-10-08（Asia/Shanghai）。2026-10-09 补齐取证适配修复后，以第九版生成头 / 第二版公共工具适配协议已完成完整 96 次模型验证及独立复算；工程验收通过，领域专家复核仍待完成。统一进度见 [plan.md](../../plan.md)。历史 96 次及 20 / 4 / 8 次复核继续保留，不能将不同协议的结果拼成成功率。

## 为什么第四版仍未通过

第四版解决的是 JSON 层级和有限参数结构。最新 8 次都可解析，但仅 2 次通过 Validator，1 次匹配未审参考，说明生成结构正确与调查方案有效仍有距离。逐例原文、引用对象和来源定位符核对后，主要原因如下。

| 原因 | 直接证据 | 修复 |
|---|---|---|
| 把“可见”当成“可引用” | 案例 15 的四方法将无可信目的映射的 K 用于身份、接口、配置等多步 | 根据方法已取得证据的来源、版本、权限、时效、适用目的编译生成前许可；不适用材料仍展示并记录原因，禁止引用 |
| 引用不随动作和对象约束 | no-graph 案例 23 双侧核验引用 SMF-B 的 K，Validator 按原规则拒绝 | 引用按动作及目标收窄：配置仅同对象适用 K，接口/日志仅同对象 R，映射仅相关两侧 P；人工出口无已知事实引用 |
| 人工出口只是提示，缺少真实缺口清单 | Direct 案例 23 在 8 步中做了两次映射核验，却省略补证动作 | 从可见记录识别缺失、字段拒读、时效、冲突和两侧错配；输入明确缺口，最多一个双侧核验，保留补证出口 |
| P5 提前结束取证 | 案例 1 / 23 只有 R/P，仍用 R 支持配置检查 | 只改公开合成 backend 的自主规划提示，明确配置任务必须尝试手册来源及调查来源；保留原 LangGraph、缓存、预算、工具选择和失败，不强制预取 |
| Schema 重复占上下文 | 第四版将展开 Schema 同时放到提示和服务端，实测接近 180 秒 | 服务端保留 Schema；提示只保留字段说明、可信上下文、有限动作及证据；输出必需字段与完整 citation 不省略 |
| 参考尚未独立复核 | 24 例 reviewed=false，前 10 例只有校准候选，无双评 | 导出双评表及 hash 校验入口；实际评审记录为 0 时继续保留 null VPR，不把机器参考匹配改名为专家通过 |

其中跨对象拒绝不是本轮发现的误拒：原文引用的是对端 K，而动作只允许对端 P。Validator、Translator、IR、action registry、参考分支及匹配规则均不改动以换取通过。运行前逐文件不变证明见 `runtime/v8-next/phase2/closure-evaluator-invariance-001.json`。

## 生成前修复的范围

新增 `plan_capabilities.py`。它只使用当前方法实际取得的 bindings、已登记适用性映射、物理来源和任务元数据，不读取参考草稿、注入标签或 v8 的 Contract 状态。配置检查须有同对象适用 K；未知/错版/过期/被撤销映射不能变成 Known。权限不足时保留其他合法检查并提出补证/人工出口，不靠全部拒绝规避问题。

共同生成头按照对象和动作约束参数、引用及身份依赖。第八版起，必需动作流程由任务模板和已取得证据确定，模型负责自然语言文本、可用知识引用及 REQUEST_EVIDENCE/HUMAN_REVIEW 出口选择，不能增删槽位。原始 JSON 仍全部由模型生成，未经修改地交给 Translator 和独立 Validator；不在生成后补步骤、依赖或引用。前置条件在这个只读调查头中限为空，使用停止条件处理未来未知；IR/Validator 对一般三值前置条件的支持及反例保持不变。

这个头包含共享的确定性流程先验，因此新结果评价的是“方法 + 相同任务流程/证据许可生成头”。结构完整性含模板保证，不是 LLM 自主规划能力的证明；不能把先验的拦截贡献归因于 v8 图或离线 Gate，未来自由规划对照需单列协议。对不可用材料的排除、来源回查及 registry 读取时间都计入共同 180 秒；dispatcher 不代表物理读文件次数，后者继续 N/A，不推算来源 IO 优势。

流程依次包含授权对象身份、任务声明的接口/日志调查、适用 K 支持且字段可读的配置检查、一个双侧核验以及实际缺口出口。双侧核验依赖两端身份；补证参数包含完整实际缺口清单；无缺口时不生成补证。输入不包含参考分支或案例注入标签。固定流程超过 8 步会拒绝，不静默裁去必需步骤；本轮 24 例均为受支持的两对象模板。

## 复跑中新发现的反例

1. 第五版首先生成固定 step_id，服务端分支据此锁定 CHECK_IDENTITY；首例 8 步反复使用 id1/id2，文本却写接口检查。`closure-full-001` 完成 1 次后中止，来源全程未变，原文/未完成请求及 SHA 封存。第六版将动作及目标放在 ID 前，真实首例恢复 6 个必需步骤及 4 条依赖。
2. 第六版常规 N4 原文虽然机器通过，却在缺口清单为空时提出补 MTU。该错误不靠修改评分掩盖：`closure-full-002` 完成 2 次后中止并封存。第七版在无缺口时禁用补证动作；有缺口时 missing 只能逐字取自当前缺口清单，并明确不凑满 8 步。

3. 第七版 `closure-preflight-003` 完整执行原案例 1 / 15 / 23 × 四方法，共 12 次：全部可解析，9 次通过 Validator 与草稿匹配；3 次未知 K 方案重复身份步骤。禁止配置后，非法 CHECK 前缀仍可能被解码为合法 CHECK_IDENTITY，提示“不重复”没有解决流程问题。12 份评分/成本复算一致，核验 358 个新文件与 2,793 个旧文件 SHA。

上述两个中止批次不能当作完整 96 次试点，也不能因通过机器评分而删除错误。第七版失败说明必须把必需流程与单步许可同时落地；第八版使用服务端 prefixItems 限定流程，保留两种合法出口。全量复跑使用新 ID，不能就地续跑或替换失败。历史及本轮失败清单：`closure-failure-inventory-002.json`。

## 验证安排及真实评审入口

第八版在原案例 15 × 四方法完成 4 次真实预检：4 份均可解析、通过 Validator 与未审参考；评分/成本复算一致，126 个文件 SHA 核验。源代码全程不变，VPR 仍为空。结合本机实际 xgrammar 编译器/匹配器完成 24 个合法控制保留、72 个缺步骤/重复身份/越权目标控制拦截，新增模型调用 0。最初控制串因 const 数组内部空格不符合 backend 的固定字面量而失败，失败记录保留；最终用实际生成头的紧凑格式核验，不宣称任意排版均可被解码。

第九版补齐两项观测：向模型展示来源已核验的 R/P config_version，使错配理由可复核；实际 elapsed 不再被 remaining 的 0 下界截成 180 秒，超时依然阻断派发。新增时限边界回归，全量 **539 passed / 41.63 秒**、Ruff 通过。第九版源 SHA 为 `682ac6049c462a0da54d2b943b5464dbef96a32e92341dfe100e27d1c626af9b`，快照 `closure-code-freeze-005`。

第九版 `closure-full-003` 完成 25 次后，发现 v8 日志/对端查询被错误的空设备范围拒绝：25 次机器通过不能证明取证成功，因此批次中止并封存。

根因在 `CommonToolV8Engine._collect`：旧工具校验器要求 `device_ids` 或先前原生证据确立设备范围，而 wrapper 每次均传空范围及空 known。修复为每条已经编译并授权的查询传入其单个目标设备，公共后端仍检查 OrchestrationTask 的 PermissionScope。故障前新增取证覆盖回归失败，修复后 18 项运行器测试通过。未改旧 AgentEngine 或放宽旧权限规则。

同时，普通合成 K 将运行观测窗带入知识绑定，图 K 不含该观测窗，引发相同知识的窗口规范化缺口。公共工具第二版仅对 R/P 保留运行观测窗；K 仍核对知识有效期、版本及登记适用性，原始来源包完整保留。正常案例现在要求两对象 K/R/P 实际覆盖、所有 Contract 状态 satisfied、头输入无缺口，而不是只看最终方案评分。补充实际收集链专项：24 种输入 × 有图/无图 = **48 次**，新增模型调用 0；错误 scope_denied 为 0，全部实际缺口类型符合预期，拒读字段未泄漏。证据 `closure-source-coverage-control-001/proof.json`。
