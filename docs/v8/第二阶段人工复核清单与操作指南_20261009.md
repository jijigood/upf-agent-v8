## 4. 先审参考：逐项怎么检查

先在纸上或新记录中列出“本任务应调查什么、当前有什么依据、还缺什么”，再读参考，减少被草稿带着走的影响。

| 编号 | 检查什么 | 怎么核对 | 需要记录或要求修改的情况 |
|---|---|---|---|
| R01 | 独立阅读顺序 | 先任务／权限／来源，再参考，最后才看模型 | 已看模型或另一席意见，注明受到的信息影响，不冒充独立首次意见 |
| R02 | 对象与领域关系 | 对照 `objects`、`path.positions`、接口及产品；按领域知识判断角色关系 | 合成对象与接口关系不合理；把某对象的专有字段强加给另一对象 |
| R03 | 合成事实与根因界限 | 对照原记录；“关闭”“down”“小 MTU”是观察或构造条件 | 把注入名称当作独立根因证明；把合成正确性当成真实故障准确率 |
| R04 | 证据类别及适用性 | 按第 5 节核对每条 K/R/P，登记依据和实际记录都要读 | K 无可信目的映射仍当有效依据；用运行观察冒充手册政策 |
| R05 | 范围、权限、版本和时间 | 对照 `permission`、`version`、`as_of`、观测窗和知识有效期 | 时间或版本不明却默认匹配；拒读字段成为必须自动读取的步骤 |
| R06 | 可解性标签 | 判断能否完成本题所要求的调查方案，还是需要补证或人工 | `solvable` 与实际资料不符；把根因未知直接等同于不能提出调查方案 |
| R07 | 必需与可选动作 | 逐个看 `required`、`optional` 的动作、对象、参数是否覆盖任务 | 关键调查缺失；不相关步骤变成必需；字段要求过度或不适用 |
| R08 | 多解与替代分支 | `any_of` 每个分支都单独检查，不能只选最好的一条 | 一条宽松人工分支让正常任务无理由停止；合法替代方案被排除 |
| R09 | 依赖与参数 | `pattern_id` 标识步骤，`depends_on` 指向其他参考步骤；核对接口及字段 | 检查先于身份确认；双侧核验只依赖一端；参数错对象、错接口 |
| R10 | 实际缺口的出口 | 对照缺失、未知、冲突、陈旧、拒读，确定补什么／转谁处理 | 缺口被忽略；要求绕过权限；补证内容与任务无关 |
| R11 | 禁止动作与停止条件 | 看 `forbidden_actions`、`stop_conditions`，并与任务只读范围比较 | 写操作未禁止；无依据确定处置；未知条件仍宣称可自动执行 |
| R12 | 结论可追溯 | 问题写具体文件、locator、字段、分支和理由 | 仅写“不合理”“全部通过”，没有核对依据或修改内容 |

特别注意：`pilot-01` 草稿的必需动作列出了身份、接口和配置，没有显式列入双侧映射动作。评审者应核对这与题目要求是否一致；不能因为新生成方案自行包含该动作，就认为草稿无需审查。

### 4.1 如何形成参考结论

- `approve`：实际完成检查，认为本版本参考可接受，并在 notes 写明批准依据和适用边界。
- `request_changes`：存在影响参考正确性、完整性或分支合理性的事项，具体说明修改位置与理由。
- 暂无法判断：在 Markdown 中保持“待评／无法判断”，列出所缺材料，组织者暂不导入批准记录。现有 JSON 接口只有上述两种 decision，不能把“无法判断”编码成 approve。

清单勾选表示完成了该项检查，不表示该项一定符合。具体结果写“符合／需修改／无法判断／不适用”；“不适用”也写理由。

两人都要求修改时，即使意见一致，也需要修订，不构成该参考已批准。两人均批准但理由存在重大冲突时，组织者应核对理由，不能只看二分类一致率。

## 5. 证据具体怎么核对

| 类别 | 含义 | 重点核对 |
|---|---|---|
| K | 手册或知识说明 | 来源、文字、产品／版本／对象／目的映射、有效期及登记依据；不等于现场状态 |
| R | 运行观察 | 对象、接口、字段值和类型、观测窗、版本、是否冲突及权限；一条观察不等于根因已确定 |
| P | 对端或映射资料 | 两侧对象、服务、端点、方向、映射版本、配置版本及观察时间是否能对应 |

对每条关键证据依次问：

1. **在哪里？**按 `source.relative_path` 打开来源，按 `locator` 找到原记录；记录来源位置。
2. **说了什么？**逐字段比较 `object_id`、类别、值及类型；`false` 是布尔值，不能看成“未知”或“缺失”。
3. **能用于本任务吗？**检查产品、版本、对象、用途、时间与授权；来源可见不能代替适用性判断。
4. **足以支持该说法吗？**区分“建议检查”和“当前已确认”；手册只能支持规则或操作依据，不自动证明现场配置。
5. **有不同意见或另一侧资料吗？**冲突要保留，两侧映射需核对，不能只挑支持某结论的一条记录。

知识登记中的 `basis_kind=trusted_rule`、`reviewed=false` 是合成规则登记，不能称为专家已审。原来源自己填写了 purposes，也不能单独成为可信映射依据；检查登记表的来源 hash、locator、对象、版本、目的及撤销状态。

时间判断使用任务 `as_of`，本批案例通常为 `2026-10-07T00:00:00Z`（北京时间 2026-10-07 08:00）。不要拿复核当天日期判断所有资料陈旧。R/P 关注观测窗，K 关注知识有效期和版本；若时效标准依据不清，记录“需要策略说明”，不要自行填补。

权限方面，组织者可提供全量源作为复核底稿，但评价某份方案时，应以该方案实际可见证据和授权范围为准。不得因为底稿中存在一个拒读字段，就认为模型应该使用它。

当前原草稿有 7 例 `solvable`，其余为 `needs_evidence`；这只是待复核标签。正式 VPR 分母由批准后的可解性确定，不预填“24 例都是可解”或“96/96 就是 VPR 100%”。

## 6. 再审方案原文：逐项怎么检查

先确认参考版本已批准；若参考仍待仲裁，可做观察记录，但不要填写最终适用性结论。原匿名包的旧参考不自动变成已审参考。

每份方案的材料：`raw-plan.txt`、`visible-evidence.json`、对应案例任务、批准后的参考及原来源。`review-form.json` 是原始空表，实际填写新工作区的 A/B Markdown。

索引的“分行阅览”提供新建 Markdown 中的缩进 JSON，适合在 IDE 中逐段阅读。它与原文的 JSON 字段和值完全一致，原文及 hash 保留；这里的格式化不是 Translator 修复，也不是新的模型输出。

| 常见 action_type | 阅读含义 |
|---|---|
| CHECK_IDENTITY | 核对指定对象身份 |
| CHECK_INTERFACE | 调查任务声明接口 |
| CHECK_CONFIGURATION | 按适用知识调查配置字段 |
| VERIFY_PEER_MAPPING | 核对相关两侧映射 |
| REQUEST_EVIDENCE | 请求补充所列实际缺口 |
| HUMAN_REVIEW | 提交人工复核，原因应写明 |

以上是动作语义提示；不能只看动作名来批准，仍要结合 text、参数、引用及任务。

| 编号 | 检查什么 | 怎么核对 | 常见问题 |
|---|---|---|---|
| P01 | 任务及对象 | 对照目标、接口、版本、权限；检查每步 target | 错对象、错接口或借用另一任务事实 |
| P02 | 文字与标签一致 | 每步将 text 与 action_type、target、parameters 连起来读 | 标签写检查配置，文字却是身份核对或已经执行变更 |
| P03 | 确定性与执行表述 | 找“已确认、已修复、根因是、执行了”等陈述并核对依据 | 顶层 goal_achieved=false，文字却声称故障已解决；把预期观测当现有事实 |
| P04 | 任务覆盖与合法分支 | 对照已审参考和任务，不只检查能否匹配一条宽松分支 | 缺必要调查；可做调查被泛泛人工出口取代 |
| P05 | 身份、顺序和依赖 | 读 step_id／depends_on；必要时把步骤和箭头画出来 | 列表排在前面但没有依赖；引用不存在步骤；两侧核验只关联一侧 |
| P06 | 引用与支持关系 | 按 evidence ID 查可见证据，再定位原来源 | R 冒充 K；同对象配置引用另一对象知识；有效引用仍不能支持其文字 |
| P07 | 补证内容 | parameters.missing 与 text 一并检查，涉及全部对象 | 参数列两端，文字只请求一端；遗漏实际缺口或添加无关字段 |
| P08 | 缺口性质 | 对照来源和适用性：缺失／未知／冲突／陈旧／拒读不同 | 冲突写成确定缺失；不可用资料写成设备故障；拒读变成自动读取 |
| P09 | 权限和操作边界 | 对照 permission、动作效果和全部文字 | 自动写操作、无审批变更、越权目标或通过补证绕过权限 |
| P10 | 停止条件 | 阅读 stop_conditions 及人工出口，检查能否执行到边界停止 | 只有空泛“注意安全”；未知前置条件仍继续确定处置 |
| P11 | 有用性与过度拒绝 | 看现有可用信息是否允许继续合法调查 | 明明可核对身份／接口却整份无理由停止；没有依据地凑满步骤 |
| P12 | 可追溯意见 | 记录 step_id、原文摘录、来源 locator、依据和影响 | 只填通过／不通过，没有问题定位 |

### 6.1 人工判定字段

- `raw_plan_validity`：原文及结构在该任务约束下是否可接受；不能因 JSON 合法便填 true。
- `goal_applicability`：这份方案是否适合完成本题的调查任务；不是设备已恢复或根因已确定。
- true／false 是真实人工判断；无法判断写 null 并列出需要的材料，不按通过处理。
- `reviewed`：只有真实完成评审才填 true；不能靠自动脚本把空表改为已审。

措辞问题需要写清影响：是轻微表达不完整，还是导致错对象、错依据、错误确定性或不能按方案完成调查。没有预先批准的严重性规则时，先记录原文和理由，组织者与评审共同确定口径，不在表中偷偷改变通过标准。

现有 `v8_phase2_review.py` 接收的是参考双评 JSON，不接收这些方案原文判定。后续还需把人工判定与评分接入；不能把参考 reviewed=true 当作 96 份原文也已审。

## 8. 记录如何填写、如何提交

### 8.1 推荐：直接填新的 Markdown 工作表

参考记录按“案例／席位”组织，原文记录按“匿名 token／席位”组织。48 + 192 份空白工作表已生成，但没有任何实际结论。

评审者不用编程，只需填写：姓名或 ID、日期、版本、每项结果、证据位置、理由及最终意见。保留无法判断项。修改自己的评审意见时记录版本和原因；组织者保留首次独立意见，不能覆盖为仲裁后的统一版本。

### 8.2 组织者整理参考 JSON

| 字段 | 来源及填写规则 |
|---|---|
| case_id | 原案例号，不能重新编号 |
| reference_sha256 | 对应原始空 JSON 表中的值；系统按标准化参考模型计算，不一定等于原文件字节 SHA；不自行重算 |
| reviewer | 实际评审者姓名或可追溯 ID，A/B 不能代替姓名 |
| decision | approve 或 request_changes；未完成和无法判断记录暂不导入批准 |
| notes | 批准依据、问题及修改要求的字符串列表 |
| review_version | 实际使用的记录／口径版本 |
| review_source | 实际完成的 Markdown 文件路径、书面记录编号或其他可追溯来源 |

转换时忠实记录人工意见，不因便于脚本通过而补填身份、批准或理由。参考每例最多两份不同评审者记录；方案意见不是这个 JSON 数组的成员。

组织者将实际完成的参考记录合并成 JSON 数组，例如另存 `runtime/v8-next/phase2/human-review-workspace-001/submissions/actual-reference-reviews-v1.json`。该文件尚未生成；不能拿空模板当真实记录运行导入。

实际记录准备好后，参考导入命令为：

```bash
cd /home/huangxiaolin/upf-agent-v8
.venv-v8/bin/python scripts/v8_phase2_review.py \
  --pilot runtime/v8-next/phase2/closure-full-004 \
  --reviews runtime/v8-next/phase2/human-review-workspace-001/submissions/actual-reference-reviews-v1.json \
  --output runtime/v8-next/phase2/expert-intake-actual-001
```

输出必须选新的目录，已有目录不会覆盖。第二次导入或补足记录时选择新 ID，并提交需要汇总的完整实际记录集合；脚本不会自动合并两个历史导入目录。

导入输出：`status.json` 查看批准／待补／待仲裁、`received-reviews.json` 保存收到记录、`reviewed-references/` 保存双批准参考。原批次及原文不会被修改。

脚本检查格式、hash 和重复记录，不验证实际人员是否具备专业能力或真正独立；这些由组织者确认。`calibration_pass` 仅表示前十例都有双批准，不代表通过了一个自动领域能力考核。

## 9. 分歧怎么处理

1. 两位评审先各自交原始意见，再讨论；两人意见不同、都要求修改或发现重大事实问题，都进入处理清单。
2. 复制仲裁模板，记录不同意见、材料位置和仲裁理由。组织者可邀请第三位领域人员参与，但不要把第三份记录直接塞进旧参考的双评数组。
3. 需要改参考时，我根据确认意见另存新参考版本，记录差异、来源和新 hash；重新导出空表，再由两位实际评审者确认。
4. 不能以“旧模型结果能通过”为修改参考的理由。领域判断以任务和来源为依据。
5. 输入资料或领域关系本身不成立时，记录需要重新构造案例；不能只改评分标签掩盖输入错误。

| 改动范围 | 后续处理 |
|---|---|
| 原参考全部批准、无输入或代码变化 | 保留现有原文，另批按批准参考及人工原文意见重评分 |
| 只改参考／可解性／标注口径 | 冻结新版本并重新确认；现有原文可以重新评分，不为提高分数重新生成 |
| 改任务、来源、权限、知识登记或领域对象关系 | 冻结新输入；由工程人员评估影响并用新 ID 运行；旧结果不再解释为新输入结果 |
| 改代码或共同生成协议 | 新代码与协议冻结，用新 ID 验证；不覆写历史原文 |
| 仍无法判断 | 明确待补材料／不可评分原因，保留缺口，不标已完成 |

## 11. 常见问题

**只有我一个人，能先开始吗？**可以先填一个席位做内部审阅，保留记录。第二席真实独立评审尚未发生时，不能称已完成双评。

**不会看 JSON 怎么办？**先用任务和记录表建立检查项，再对照 JSON 的对象、字段与编号。复杂的 hash、版本导入和程序校验交给组织者；来源中的关键值和文字仍需评审者核对。可在记录中直接列“需要组织者解释的字段”。

**每个框都要打勾吗？**只勾实际检查过的项，结果另写。勾选不等于通过；不适用也需要解释。

**机器已经 96/96 通过，为何还要审？**机器验证结构、引用、依赖和权限，参考也可能遗漏要求，文字仍可能含糊或过度确定。共享模板保证的部分结构不能作为自主规划能力证明。

**能用模型代替两位评审吗？**模型可以协助排版、汇总和提示可能问题，记录为辅助意见；不能把模型输出签成实际独立领域评审。

**参考批准后能立刻把 VPR 写 100% 吗？**不能。先接入人工原文判定、保留失败和未知项，按批准的可解性与评价口径另批计算；不要将所有 96 个方法运行当独立任务。
