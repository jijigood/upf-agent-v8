## 3. 三个边界问题如何被修正

**F1，旧动作批次：** `batch_id` 现在代表当前认证批次，`computed_batch_id` 代表计算来源。无变化时可以不重算，但全部发布动作都必须取得新批次认证。原 `semantic_results` 继续作为历史语义口径；新验收使用 `complete_results`，不会将 batch 和评估上下文排除。

**F2，时刻不一致：** `full_actions/gate` 新增显式 `now/context` 输入，所有证据选择使用 `EvaluationContext.as_of`。若状态是在另一时刻认证，Gate 会拒绝将其当当前结果。原回归中的 Full oracle 已补传实际 `now`，避免继续沿用旧时刻错误。

**F3，初始漏边：** 初始 Full 评估使用读取追踪器，逐 reader 保存实际读取集合。即使损坏构图器将缺边索引重新声明为完整，独立 Full 读集仍能发现遗漏。上下文重建和 fallback 重新采集读集；新增分支的实际读边仍由更新时审计检查。

审计覆盖当前确定性规则的实际读取及已有声明依赖，不声称能证明任意未来动态代码所有分支的依赖完整性。后续新增领域规则时，应加入对应分支测试和保守声明依赖。

两个旧的漏读边测试现在期望更早的 `incomplete_read_index`，而不是等到执行 reader 后才触发 `undeclared_actual_read`；阻断条件加强，没有降低验收要求。

## 4. 计数协议与兼容性

计数边界是 **dispatcher**：

- `attempted`：获得调用预留，进入调度尝试；崩溃后的实际外部传输是否发生可能未知。
- `committed`：结果已持久提交；失败结果也可以有提交回执。
- `reused`：读取已有提交结果，没有再次调用后端。
- `error`：调用异常或明确的失败回包；可与 committed 同时存在，不能把各状态直接相加当调用次数。
- `blocked`：预算不足、未提交回执需要复核等原因阻止调用；不计为一次新后端调度。

提交结果和事件在同一 SQLite 事务中保存，事务失败不会留下虚假的计数。重复提交不重复计时或计数；幂等 key 不能变更请求或 tool/model 类型。模型 usage 缺失时 token 总量写 null，历史无事件的回执标记 coverage incomplete。物理源读取、检索缓存和 GPU 占用尚未观测，保持 null。

`MeasuredBackend` 在测试中验证了输出透传、异常、失败回包与缺失 token 的处理；**本阶段没有运行完整 P5 规划者**，不能把它表述成已完成公平 P5 对照。下一阶段会将该包装器接入共同证据源和实际 P5 runner。

每个引擎运行目录新增 `metrics.json` 与 `metrics-traces.jsonl`；原预算仍按唯一 Ledger 回执计算，复用事件不会额外消耗工具或模型预算。

新增字段对旧 JSON 有默认值，但旧状态缺少当前认证上下文时不会被 Gate 当作当前可信状态。历史运行继续使用其冻结代码/配置回放；新源码指纹不应与旧验收数字混用。早期可行性探针保留为历史审计材料，升级后的验收入口使用下面的新命令及专门回归测试。

cd /home/huangxiaolin/upf-agent-v8

  --output runtime/v8-next/phase1/freeze-user-001

  tests/test_v8_phase1_updates.py \
