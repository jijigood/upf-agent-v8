# E1 领域只读候选协议与采集说明

日期：2026-10-11。本版是工程校准接口，使用现有 validation 的正常采集资料，不建立正式 Gold，不读取 heldout。默认正式计划头、旧动作注册表和旧 PlanIR 保持原协议。

## 输入、权限与对象归属

`scripts/v8_e1_domain_readonly.py prepare` 只访问12个 validation 目录，将其正常 `snapshot.json` 逐字节复制到另一个工程数据目录。原60例的输入、任务、权限、来源准入和审核登记不修改；本版不是原任务在原权限下的复测。

每个工程任务有独立的 `domain-scope.json`。其 SHA 内容绑定到任务权限 revision，原始正常快照另以 SHA 锁定。UPF 使用 core 命名空间的 `ogstun`；UE 使用 ue 命名空间的 `uesimtun0`，明确新增 UE 对象及授权；RAN 仅使用 core 内 `gnb.log` 的日志窗口，不继承 UPF 接口或 UE 探针字段。对象产品分别为 Open5GS 2.7.6 和 UERANSIM 3.2.7，这些工程档案仍需实际领域适用性确认。

允许字段按对象分别限定。只从正常快照提取接口、日志、已记录探针和 PCAP；不会打开 `private/external-verification.json`、注入记录或故障真值来补全模型可见字段。原12份正常快照的 filter 计数和独立 UE PCAP 都缺失，保持缺失，不以空集合或私有读回替代。

## 五个候选动作的边界

注册表为 `v8-e1-readonly-registry-candidate-1`，命名空间权限为 `v8-e1-namespace-scope-candidate-1`。旧注册表没有增加这些动作；旧 Translator 不能将其作为旧正式计划接收。

| 动作 | 所需资料与限制 |
| --- | --- |
| `READ_TUN_INTERFACE` | 对象所属命名空间的指定 Linux 隧道接口；不将 ogstun 冒称为 N3/N4 接口 |
| `READ_FILTER_COUNTERS` | core 的 filter 表 INPUT、OUTPUT 或 FORWARD 链；正常读回命令固定为 `iptables -nvxL CHAIN`，返回码非0仍为缺证 |
| `READ_SESSION_PROBE` | UE 的已记录会话日志和指定探针；不发送新探针，不自动把会话建立或故障原因标为已证实 |
| `READ_PACKET_CAPTURE` | 授权捕获位置、SHA、包记录数、截断和时间窗口；不解码或匹配报文 |
| `COMPARE_CAPTURE_WINDOWS` | 两个独立命名空间的捕获来源、非空、完整性和时窗重叠；不证明报文对应、送达或端到端通路 |

动作参数均采用有限枚举与只读效果，没有自由命令、路径、写操作或自动执行接口。领域检查必须依赖同对象身份步骤，跨对象比较必须依赖双方身份。默认全部方案为未执行、不可执行的建议。

`basis=inspect_existing` 要求被独立 Validator 接纳、与正常原文一致、适用产品版本和时窗、字段及选择器完整的引用。`basis=collect_then_check` 要求明确待取得或待核验的缺口，并且引用为空。当前实际输入的 `corroborated=false` 不修改，因此只读获取了物理资料也不自动获得可信事实准入。

独立 Validator 重新检查正常投影和原始快照，不复用生成器的准入结论；会拒绝已被改写但自身 JSON/SHA 一致的伪投影、跨命名空间或设备越权、失败的过滤链读回、重复步骤、缺失身份依赖、不完整双侧捕获和写操作。单元正控使用明确标记的合成固定资料，不算真实来源批准或专家审核。

## 候选计划头与四方法接入

候选计划头版本2统一所有动作分支的字段顺序：`action_type → target → step_id → text`。紧凑 xgrammar 按属性顺序解码；版本1的新动作首先解码 step_id、旧动作首先解码 action_type，一旦选择 step_id 开头就无法再选择旧身份动作。实际离线 GrammarMatcher 已验证这一差别。版本1整批12次原文、失败、费用和源码冻结独立保留，版本2另版运行，不合并分母或修补原文。

版本2保留自行选择动作、1～12步、对象、顺序和依赖，没有必需步骤槽位或参考覆盖约束。固定模型、temperature=0、头部最多3072输出 Token；任务总预算为8次模型、8次工具、3轮、180秒。Schema 的语义摘要采用规范 JSON，另存原始序列化摘要；实际请求的 EBNF 逐份重新编译核对，以锁定影响解码的属性顺序。

四方法都在原生流程前执行两个相同的 `read_domain_snapshot`（UPF、UE），计入各自工具预算和耗时。原生 Direct、P5 和两个 v8 的调用、失败及费用继续保留。P5 的原生工具目录没有替换为这些新动作；这两个读取是共同前置准备，不是 P5 自主选择或完成了领域工具闭环。新动作目前表达计划，并由共享正常资料读取器提供输入。

本轮预登记 N001、N002、N003 三份已有 validation 输入，各四方法，旋转执行顺序；报告名称为 `engineering_validation`。原始问题统一为明确扩大权限后的只读调查问题，故与此前固定五步骤48次校准不构成同协议质量对照。输入的来源准入、技术真值及专家评分尚不完备，reference match、solvability、正式 VPR 均为 null。

三个工程输入没有可用 P3 索引，full 路径会记录 `graph_unavailable`。其尝试和费用仍计量，但本批不能用来证明完整图机制的质量收益。独立拓扑来源及可采信的关系资料仍需补齐。

## 正常采集器联调

`lab/e1/readonly_control.py` 仅公开固定正常快照、抓包开始与结束入口。`scripts/v8_e1_readonly_capture.py` 创建有归属标签的内部 Docker 网络和两容器，使用固定镜像；启动网络功能和测试 UE、发送健康探针属于实验 harness。模型与 Agent 没有执行启动、探针、注入或修复。

成功的健康联调003从正常快照直接取得三个 filter 链，以及 core 和 ue 各一份独立 PCAP，并通过投影和共享只读工具接入。来源仍为未批准状态。包数和未截断仅描述所保存的记录，不保证采集无丢包或覆盖全部探针，不作报文匹配或送达证明。原12份 validation 输入不会追加本次不同时间窗口的记录。

前两次联调各有采集后 API 接线错误，原文件、失败和清理回执独立保留；003另采。每批临时资源均按归属回收。三批都是同平台健康控制，不新增正式故障案例，不用于增加案例数或独立来源数。

## 复现与下一步

以冻结目录内对应版本源码、输入、协议和真实请求为准。只读复算使用 `runtime/v8-next/e1-domain-readonly-20261011-001/audit_domain.py`，可核对原文、完整 Validator、调用账本、预算、实际语法和配对工程成本；重放旧批时应使用其 `code/src` 内冻结版本。

专家后续应分别确认原始故障事实、对象和命名空间归属、产品版本、正常采集覆盖、必要动作及允许替代路径、未知信息出口和来源准入。现有12份 validation 编制资料及24行双评空表在前阶段目录；不能将本轮工程校验、合成正控或正常资料读取记为人工批准。完成独立 Gold 和真实双评后，再冻结正式 validation、复核实际原文，最后单次运行原24份 heldout。
