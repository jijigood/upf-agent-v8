# P0 资料、旧行为和缺口记录

审计产物由 `uv run upf-agent p0-audit` 写入 `data/p0/`，关键快照保存在 `evidence/p0/`；该命令只读原始资料，不连接 Dify API 或运行数据库。以下统计来自 2026-09-25 的运行。`sources.json` 为资料哈希和结构清单，`workflow_nodes.json`/`workflow_edges.json` 为 35 节点/32 边映射，`workflow_prompts.json` 保留原提示词，`legacy_log.py` 为从 YAML 提取的原日志代码，`legacy_baseline.json` 为原日志规则输出。

## 当前业务事实

工作流有 8 个 LLM 节点，其中 7 个配置为火山引擎 `DeepSeekV3.1`，1 个配置为 `Qwen/Qwen3-32B`；分类器、参数提取器另用 Qwen。四个检索节点引用四个不透明知识库 ID，不能由此证明四份 DOCX 与四个知识库一一对应。网管分支仅提取并回答 JSON，没有调用真实网管 API 的节点。

路由对应关系：MML 与 CLI/VPP 各做至多三条查询扩展、逐条知识检索与会话变量累积；产品问题直接检索；故障问题做参数提取、日志/拓扑文档抽取、规则分析、检索、解释；网管问题只返回参数；其他问题直接生成。新系统的去向已写入 `workflow_nodes.json` 的 `migration_component`。

## 文档覆盖

四份 DOCX 共 126 个原生表格、871 行、58 个文本框、472 个实际媒体文件；紧急故障指引有 52 个文本框。`set-log-level` 和 `upfmgr mml` 在四份文档的原生 OOXML 文本中均未检出，图片内容尚未 OCR，因此只能记为“现有原生文本未覆盖”，不能宣称原四个知识库一定缺少它们。现有手册里还包含其他网元资料，检索必须过滤产品和版本。

## 日志旧行为基线

`upfd_masked.log` 为 6,347,974 字节、32,539 非空行；现有时间格式全部解析，发现一处相邻时间倒序。旧规则未分类 25,979（79.84%），PFCP 会话释放 5,715，GTP-U 探测 382。其余类别见 `legacy_baseline.json`。

已有明确错误：旧“PFCP节点不可达”37行中，23行只是接收心跳请求；11条“许可证未安装告警”其实均是解除记录；3,238条 FAR 切换格式行在脱敏后与旧正则不匹配。旧时间结束边界 `23:59:59` 漏小数秒，旧拓扑匹配用整行包含 N3/N4 容易误命中 N30。新系统故意修正这些语义，不能要求新分类计数等于旧结果。

## 评测状态

`eval/slots.jsonl` 有 120 个**待标注名额**与建议类别/暂定拆分，`eval/protocol.md` 定义标注、分组冻结、指标和工具边界。它尚不是完成标注的 gold set；所有新模型与检索效果指标在人工复核前均为待测。
